이 글은 2026년 4월 10일 기준, 내가 직접 써 본 환경을 바탕으로 정리한 개인 메모다.
주로 본 코드베이스 작업, 문서 작성, UI 시안 확인, API 호출 기반 사용 경험을 기준으로 적었다.

요즘은 AI 모델 자체보다도 어떤 프로바이더를 어떤 용도로 붙여 쓰는지가 더 중요해졌다고 느낀다.
비슷해 보이는 모델도 실제로 써 보면 강점이 꽤 다르고, 반대로 스펙만 보면 좋아 보여도 실사용에서는 답답한 지점이 분명히 있다.
이번 글은 내가 최근 직접 많이 써 본 몇몇 주요 AI 프로바이더에 대한 짧은 사용 후기다.

기준은 단순하다.
코딩, 문서 작업, 이미지나 UI 관련 결과물, 응답 속도, 그리고 사용량 제한을 포함한 실제 사용 경험이다.
벤치마크 정리라기보다는 "무엇을 맡기면 좋고, 어디서 스트레스를 받는가"에 가까운 기록이다.

## 먼저 한 줄로 정리하면

- 코덱스 5.4는 백엔드 쪽에서 특히 강했고, 프론트 UI 감각은 꽤 아쉬웠다.
- 클로드는 여전히 전반적으로 우수하지만, 사용량 제한이 계속 발목을 잡는다.
- 제미나이는 멀티모달 작업과 UI 쪽 인상이 좋았지만, 코딩에서는 유독 약하게 느껴졌다.
- GLM은 가성비가 매우 좋았고, 체감 성능도 꽤 괜찮았지만 API 응답 속도가 아쉬웠다.

## 코덱스 5.4: 백엔드는 믿음직한데 프론트 감각은 거칠다

코덱스 5.4는 써 볼수록 백엔드 작업에서 강점이 선명하다.
구조를 빠르게 읽고, 문제를 잘게 쪼개고, 실제로 돌아가는 코드까지 밀어 넣는 흐름이 안정적이다.
특히 API 설계, 서버 로직 정리, 테스트 보강, 기존 코드베이스 안에서의 수정 작업 같은 쪽에서는 결과가 꽤 만족스러웠다.

좋았던 점은 단순히 코드를 "많이" 쓰는 것이 아니라, 비교적 실무적인 맥락 안에서 고치는 힘이 있다는 것이다.
어디를 먼저 읽어야 하는지, 어떤 영향 범위를 확인해야 하는지, 무엇을 건드리면 회귀가 날 수 있는지를 비교적 잘 짚는다.
백엔드 기준으로는 생산성 체감이 확실히 있었다.

반면 프론트 UI는 꽤 별로였다.
기능을 이어 붙이는 것 자체는 하는데, 화면의 인상이나 배치 감각, 디테일한 스타일링, 전체적인 미감은 자주 둔하게 나왔다.
한마디로 코드로는 만들지만, 보기 좋게 만들지는 못하는 경우가 많았다.
프론트 구현을 맡길 수는 있어도, UI 방향을 같이 잡아 줄 모델이라고 보기는 어려웠다.

그래서 내 기준에서는 코덱스 5.4는 "백엔드와 코드 수정용으로는 강력하지만, 프론트 감각까지 기대하면 실망할 수 있는 모델"에 가깝다.

## 클로드: 전체적으로 우수하지만 사용량 이슈가 계속 남는다

클로드는 여전히 전반적인 밸런스가 좋다.
문장을 다루는 능력, 긴 맥락을 읽는 안정감, 코드와 설명을 함께 다루는 방식 모두 일정 수준 이상을 유지한다.
그래서 무난하게 잘하는 모델이 아니라, 꽤 자주 "확실히 잘한다"는 느낌을 주는 쪽에 가깝다.

다만 내 사용 패턴에서는 예전만큼 압도적이라는 인상은 조금 덜하다.
초기에 클로드를 쓸 때는 정말 많이 놀랐고, 특히 Opus 계열은 한동안 체감상 가장 강력한 모델 중 하나였다.
지금도 여전히 상위권이지만, 현재 내가 자주 하는 작업 기준에서는 다른 선택지와의 격차가 예전만큼 크게 느껴지지는 않았다.

그래도 기본기가 좋아서 여전히 상위권이라는 인상은 유지된다.
문제는 성능보다 사용량 쪽이다.
아무리 잘해도 마음 편히 길게 쓰기 어렵다면, 실사용 만족도는 생각보다 빨리 떨어진다.
클로드는 이 지점이 계속 아쉽다.

### Opus 4.6

Opus 4.6은 초기에 정말 인상이 좋았다.
어려운 문맥을 읽고 정리하는 능력, 코드와 문서를 함께 다루는 안정감, 답변의 밀도 모두 아주 좋았다.
내가 반복적으로 붙여 본 작업에서는 초기에 받았던 인상보다 결과 편차가 조금 더 크게 느껴졌다.

그렇다고 해서 못 쓰겠다는 의미는 아니다.
여전히 우수한 모델이고, 중요한 작업에 붙이면 여전히 기대값이 높다.
다만 과거에 느꼈던 "이건 확실히 한 단계 위다"라는 감각은 조금 약해졌다.

### Sonnet 4.6

Sonnet 4.6은 Opus보다 가볍고, 기대치 관리도 더 쉽다.
무게감은 덜하지만 결과는 생각보다 안정적이고, 일상적인 작업에서는 오히려 더 자주 손이 가는 쪽에 가깝다.
극단적으로 뛰어난 순간은 Opus보다 덜할 수 있어도, 평균적인 만족도는 꽤 괜찮았다.

결국 클로드 계열은 Opus와 Sonnet 모두 쓸 만하다.
다만 둘 다 공통으로 남는 문제는 사용량이다.
성능 평가와 별개로, 계속 쓰다 보면 가장 먼저 체감되는 단점이기도 하다.

## 제미나이: 멀티모달과 UI는 강한데 코딩은 이상하게 약하다

제미나이는 멀티모달 모델이라는 성격이 분명하게 체감된다.
이미지 관련 작업, 텍스트와 문서를 함께 다루는 작업, 여러 형식의 입력을 받는 흐름에서는 꽤 좋은 결과를 보여 준다.
단순히 기능이 많다는 의미가 아니라, 서로 다른 형태의 입력을 다루는 데서 비교적 자연스러운 강점이 있다는 뜻이다.

특히 UI 쪽 결과물은 꽤 인상이 좋았다.
화면을 보기 좋게 정리하거나, 프론트 결과를 시각적으로 그럴듯하게 만드는 데서는 제미나이가 확실히 나은 순간이 있었다.
적어도 "프론트 화면이 너무 못생기게 나온다"는 불만은 코덱스보다 덜했다.

그런데 코딩으로 넘어가면 이야기가 달라진다.
유독 개발 작업에서는 기대보다 약한 경우가 자주 있었다.
간단한 수준에서는 괜찮아도, 실제 코드베이스를 읽고 수정하거나 맥락을 이어서 안정적으로 작업시키는 쪽에서는 아쉬움이 컸다.
그래서 제미나이는 문서, 이미지, UI 같은 쪽에는 강점이 있지만, 코딩 주력 모델로 두기에는 애매하다는 인상이다.

## GLM: 가성비는 정말 좋지만 느린 API는 분명한 단점이다

GLM은 4.7부터 5.1까지 여러 모델을 써 봤는데, 전체적으로 느낀 첫인상은 "생각보다 꽤 괜찮다"였다.
특히 가격 대비 성능이 좋다.
무조건 최상위 모델과 정면 승부를 걸 정도는 아니더라도, 실제 비용을 같이 놓고 보면 충분히 매력적인 선택지였다.

성능만 놓고 보면 내가 붙여 본 작업 기준으로는 제미나이보다는 좋고, 클로드보다는 아주 살짝 떨어지는 정도였다.
즉 완전히 저가형 대체재라기보다는, 꽤 실용적인 중간 지점에 있는 모델처럼 느껴졌다.
조금만 더 다듬어지면 훨씬 더 자주 쓰게 될 가능성이 큰 계열이다.

다만 속도가 발목을 잡는다.
특히 Z.ai 코딩 플랜 기반으로 API를 붙여 쓰면 요청이 상당히 느리게 느껴질 때가 있었고, 이건 생각보다 치명적이었다.
가격이 좋아도 응답이 너무 늦으면 작업 흐름이 자꾸 끊긴다.
결국 실사용성은 성능만으로 결정되지 않는다는 점을 다시 느끼게 만든 모델이기도 했다.

## 정리

지금 시점에서 정리하면 이렇다.

- 긴 문맥, 문서, 전반적 안정감, 백엔드/프론트 등 코딩 작업: 클로드.
- 백엔드 작업: 코덱스 5.4.
- 멀티모달, 이미지, UI 감각: 제미나이.
- 가성비: GLM.

물론 이 평가는 어디까지나 내 사용 패턴 기준이다.
무슨 작업을 자주 하는지, API로 붙여 쓰는지, 웹 UI에서 쓰는지, 얼마나 긴 세션을 유지하는지에 따라 평가는 꽤 달라질 수 있다.
그래도 분명한 것은 이제 "어느 모델이 제일 좋은가"보다 "어떤 작업에 어떤 모델을 붙일 것인가"가 더 중요해졌다는 점이다.

예전보다 모델 간 격차가 완전히 벌어지는 느낌은 덜하지만, 대신 장단점은 더 선명하게 체감된다.
그래서 앞으로도 하나만 고집하기보다는, 작업 종류에 따라 역할을 나눠 쓰는 방식이 더 현실적이라고 본다.

내 기준에서 가장 실용적인 운영 방식은 이렇다.

- 구조를 읽고 수정 범위를 좁혀야 하는 코딩 작업은 코덱스나 클로드에 맡기기
- 문서 정리나 긴 맥락 설명은 클로드를 우선 보기
- 화면 인상, 멀티모달 입력, 시각 결과 확인은 제미나이를 같이 써 보기
- 비용이 민감한 반복 작업은 GLM을 후보로 두되 속도는 미리 감수하기

결국 중요한 것은 최강 모델 하나를 고르는 일이 아니라, 작업 종류에 맞는 기본 조합을 먼저 정해 두는 일이라고 본다.
