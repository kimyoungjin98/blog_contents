정처기 실기를 준비하면서 따로 관리하던 `학습일지`를 이제는 블로그 포스트로도 남기기 시작했다.
그날그날의 정답 여부만 쌓아 두면 나중에 다시 볼 때 흐름이 끊기기 쉬워서, 무엇이 안정화되었고 무엇이 계속 흔들리는지를 글 단위로 남기는 쪽이 더 낫겠다고 판단했다.

이번 글은 2026년 4월 초부터 진행한 정처기 실기 학습 세션을 한 번에 통합한 첫 기록이다.
문제를 풀면서 확인한 학습 패턴, 지금은 익숙해진 개념, 아직도 다시 물으면 흔들리는 영역을 한 번 정리해 둔다.

## 지금까지 학습하면서 자리 잡은 것

초반에는 개념을 "대충 아는 상태"와 "시험에서 바로 회수 가능한 상태"가 꽤 다르다는 점을 많이 느꼈다.
특히 정처기 실기는 정의를 알고 있는 것만으로는 부족하고, 짧은 문장 안에서 정확한 키워드를 꺼낼 수 있어야 했다.

그래도 몇 번의 혼합 세션을 거치면서 안정적으로 회수되기 시작한 것들이 있다.

- 기능 요구사항과 비기능 요구사항의 구분
- `Aggregation`과 `Composition`의 차이
- `RTO`, `LOD`, `RAID 0`, `chmod` 숫자 변환 같은 약어/개념형 문제
- `LEFT JOIN ... ON` 같은 기본 SQL 문장 구조
- C 제어문과 포인터 기초, Java의 `this`/상속 기초, Python 기본 자료형과 메서드

이런 항목들은 처음에는 힌트를 봐야 겨우 떠올랐는데, 반복 후에는 비교적 빠르게 답이 나오기 시작했다.
특히 `Aggregation`과 `Composition`처럼 처음엔 거의 새 개념처럼 느껴졌던 것도, "독립 관계인가 / 생명주기를 공유하는가"라는 기준으로 묶어 두니 훨씬 덜 흔들렸다.

## 반대로 계속 발목을 잡는 것

지금 가장 신경 쓰이는 건 UML과 SQL이다.
둘 다 아예 모르는 건 아닌데, 문제 문장을 끝까지 정확히 읽고 답을 꺼내는 힘이 아직 약하다.

UML 쪽에서는 이런 식의 혼동이 반복된다.

- `사물 / 관계 / 다이어그램` 중 무엇을 묻는지 문맥을 놓침
- `클래스`와 `인터페이스`를 문제 표현에 따라 섞어 답함
- `Aggregation`을 `Association`으로 착각함
- `Composition`과 `Realization`을 헷갈림
- `ISP`와 `SRP`처럼 약자가 비슷한 개념을 바꿔 답함

SQL은 개념보다도 문장 뼈대에서 흔들린다.
예를 들면:

- `DELETE FROM ... WHERE ...`
- `UPDATE 테이블 SET ... WHERE ...`
- `COUNT(*)`와 `COUNT(컬럼)`의 차이
- `SELECT` 결과를 중복 제거처럼 잘못 해석하는 문제
- `> ALL (subquery)`를 기계적으로 `MAX`로 바꾸려는 습관

결국 이 두 영역은 "알고 있다"보다 "끝까지 정확히 쓰고 읽는다"가 더 중요하다는 걸 계속 확인 중이다.

## 공부 방식도 조금씩 다듬는 중

문제를 많이 풀수록, 어떤 방식으로 연습해야 효율이 좋은지도 조금씩 보였다.
지금은 아래 규칙이 가장 잘 맞는다.

- 키워드/암기형은 `빈칸 추론형`
- 코드/SQL은 `원문 스타일` 유지
- 같은 문제를 바로 반복하지 않기
- 틀린 문제는 개념을 바꿔 다시 묻기
- 힌트는 정답 전체가 아니라 최소 키워드만 주기

이 방식이 좋은 이유는 단순하다.
정처기 실기에서 자주 막히는 지점은 "설명은 할 수 있는데 정답 키워드를 바로 못 꺼내는 상태"이기 때문이다.
특히 비기능 요구사항처럼 항목이 여러 개인 개념은 2개는 떠오르는데 마지막 1개가 계속 안 나오는 식으로 흔들릴 때가 많았다.

또 SQL이나 코드 문제는 괜히 튜터가 친절하게 바꿔 말해 주면 실제 시험 감각과 멀어졌다.
원문 스타일을 유지해야 문장 구조와 답안 형식을 함께 익힐 수 있었다.

## 최근 세션에서 확인한 함정 포인트

이번 구간에서 특히 자주 걸린 함정은 아래처럼 정리된다.

- `Factory Method`와 `Abstract Factory` 혼동
- 응집도 설명 매칭에서 `절차적`, `교환적`, `기능적` 구분 흔들림
- `COUNT(*)`와 `COUNT(컬럼)` 차이 회수 부족
- UML 문제에서 "클래스 다이어그램 3구획" 문제와 "UML 구성 요소" 문제를 같은 질문처럼 읽는 습관

이런 문제는 단순 오답보다도, 시험장에서 시간을 잡아먹는 패턴이라는 점이 더 신경 쓰인다.
그래서 앞으로는 맞고 틀리고만 기록하기보다, "왜 틀렸는지"를 함정 단위로 같이 정리해 두려고 한다.

## 다음 우선순위

다음 세션에서는 아래 순서로 복습할 생각이다.

1. UML: 관계, 클래스, 인터페이스, `Aggregation`, `Composition`
2. SQL: `DELETE FROM`, `UPDATE ... SET`, `COUNT(COL)`, `SELECT DISTINCT`
3. 디자인 패턴: `Factory Method`, `Abstract Factory`, `Observer`
4. 응집도: 절차적, 교환적, 기능적 설명 매칭

정처기 실기는 넓게 훑는 것보다, 흔들리는 포인트를 짧은 회차로 여러 번 회수하는 쪽이 확실히 맞는 시험처럼 느껴진다.
그래서 다음 기록도 전체 요약보다는 "무엇이 안정화되었고 무엇이 아직 불안한가"를 중심으로 계속 쌓아 볼 생각이다.
