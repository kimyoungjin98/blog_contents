## 개요

다수의 사용자 환경에서 동일한 데이터에 동시에 접근할 때 발생하는 **동시성** 문제를 해결하기 위한 세 가지 핵심 락 기법의 상세 개념과 동작 원리를 알아보겠다.

## 낙관적 락

데이터 충돌이 자주 발생하지 않을 것이라고 **낙관적**으로 가정하는 방식이다. 데이터베이스가 제공하는 물리적인 락을 사용하지 않고 애플리케이션 (Jpa 등) 레벨에서 데이터 정합성을 관리한다.

### 동작 원리

1. 테이블에 버전을 관리할 컬럼(`updatedAt`, `version`..등)을 추가
2. 트랜잭션 A가 데이터를 조회할 때 현재 버전(예: `version=1`)을 함께 읽어옴
3. 트랜잭션 B가 동일한 데이터를 조회하고 수정하여 먼저 커밋하면 버전이 상승 (예: `version=2`)
4. 트랜잭션 A가 데이터 수정을 시도할 때, 자신이 읽었던 `version=1`을 조건으로 업데이트를 시도
5. 현재 DB의 버전은 2이므로 업데이트 되는 행은 없음
6. 애플리케이션이 이를 감지하고 에러를 발생시킴

### 장점

- DB에 실제로 락을 걸지 않으므로 락 대기로 인한 커넥션 풀 점유 또는 데드락(Deadlock) 문제가 발생하지 않는다.
- 읽기 작업 비중이 높은 시스템에서 성능이 뛰어나다.

### 단점

- 충돌 발생 시 직접 **재시도 로직**을 구현해야 한다.
- 쓰기 충돌이 잦은 환경에서는 잦은 예외 발생과 롤백, 재시도로 인하여 DB에 오히려 더 큰 부하를 주고 성능이 저하될 수 있다.

## 비관적 락

- 데이터 충돌이 빈번하게 발생할 것이라고 '비관적'으로 가정하는 방식입니다. 트랜잭션이 시작될 때 데이터베이스 레벨의 물리적 락을 획득하여 다른 트랜잭션의 접근을 원천 차단한다.

### 동작 원리

1. 트랜잭션 A가 데이터를 읽을 때 `SELECT ... FOR UPDATE` 쿼리를 사용하여 데이터베이스의 해당 행에 배타 락(Exclusive Lock)을 건다.
2. 락이 걸린 행에 대해 트랜잭션 B가 조회나 수정을 시도하면, 트랜잭션 A가 커밋되거나 롤백되어 락이 해제될 때까지 트랜잭션 B는 대기(Block) 상태에 빠진다.
3. 트랜잭션 A가 작업을 마치고 커밋하면 락이 해제되고, 대기 중이던 트랜잭션 B가 락을 획득하여 작업을 진행한다.

### 장점

- 데이터의 무결성이 가장 강력하게 보장된다.
- 충돌 발생 시에 애플리케이션 단에서 복잡한 재시도 로직을 작성할 필요가 없다.
- 쓰기 작업이 많고 충돌이 잦은 환경에서는 낙관적 락보다 성능이 안정적이다.

### 단점

- 특정 트랜잭션이 락을 길게 쥐고 있으면, 다른 트랜잭션들의 대기 시간이 길어져 전체 시스템 성능(처리량)이 저하된다.
- 서로 다른 데이터를 락킹한 상태에서 상대방의 데이터를 요구하게 되면 데드락에 빠질 위험이 있다.

## 분산 락

- 단일 데이터베이스가 아닌, **다중 서버(마이크로 서비스 등)** 환경에서 공유 자원에 대한 동시성을 제어하기 위해 외부 시스템을 활용하는 기법이다.

### 등장 배경과 필요성

- 비관적 락은 단일 DB 내에서는 훌륭하게 동작하지만, 서버가 여러 대이거나 DB를 샤딩(Sharding)한 환경에서는 한계가 있다. 또한, 비관적 락은 DB 커넥션을 점유한 채로 대기하므로 트래픽이 몰리면 DB 커넥션 풀이 고갈되어 시스템 전체가 마비될 수 있다. 이를 막기 위해 DB 밖(주로 Redis)에서 락을 획득하게 한다.

### 동작 원리 (Redis 기반)

1. 여러 대의 API 서버가 공통 자원(예: 특정 상품의 재고)에 접근하기 전, Redis 서버에 락 획득을 요청한다.
2. Redis에서 해당 자원의 락을 성공적으로 획득한 단 1대의 서버만이 DB에 접근하여 실제 비즈니스 로직을 수행한다.
3. 락을 획득하지 못한 서버들은 일정 시간 대기하거나(Pub/Sub 방식 등) 실패 처리를 한다.
4. 비즈니스 로직이 끝나면 Redis에서 락을 해제(Delete)한다. 만약 서버가 다운될 경우를 대비해 락에 타임아웃(TTL)을 반드시 설정해야 한다.

### 주요 구현체

- **Redis** : Pub/Sub 방식을 사용하여 락 획득을 대기하는 스레드에 알림을 주는 방식으로, Redis에 부하를 주지 않고 분산 락을 우수하게 처리한다.
- **Zookeeper:** 분산 코디네이션 서비스로 안정적인 락을 제공하지만 시스템 구성이 무겁다.

### 장점

- 데이터베이스 커넥션을 맺기 전에 락을 제어하므로, DB에 가해지는 트래픽 부하를 획기적으로 줄일 수 있다.
    
- 여러 서버, 다중 DB 인스턴스 환경에서도 안전한 상호 배제가 가능하다.
    

### 단점

- Redis나 Zookeeper 같은 추가적인 외부 인프라 구축과 유지보수 비용이 발생
    
- 네트워크 지연, 인프라 장애 발생 시 락 해제가 정상적으로 이루어지지 않는 엣지 케이스(Edge Case)를 방어하는 복잡한 로직이 필요하다.
