## 같은 업체를 두 사람이 수정한다면?

ERP에서 업체 정보를 수정하는 화면을 만들고 나면, 한 사람이 사용하는 흐름은 비교적 쉽게 확인할 수 있다. 업체를 조회하고, 값을 변경하고, 저장한 뒤 목록을 다시 조회하면 된다.

그런데 두 사람이 같은 업체의 수정 화면을 열어 놓았다면 어떻게 될까?

| 순서 | 사용자 A | 사용자 B |
| --- | --- | --- |
| 1 | 업체 수정 화면을 연다 | 같은 업체 수정 화면을 연다 |
| 2 | 연락처를 변경한다 | 메모를 작성한다 |
| 3 | 변경한 연락처를 저장한다 | 계속 작성한다 |
| 4 | 저장을 마친다 | 이전 연락처가 포함된 폼을 저장한다 |

B가 폼 전체를 저장하면 A의 새 연락처가 예전 값으로 돌아갈 수 있다. 두 요청이 정확히 같은 순간에 서버에 도착해야만 생기는 문제가 아니다. 몇 분 전에 열어 둔 화면에서 저장해도 발생한다.

수정한 필드만 보내면 다른 필드를 덮어쓸 가능성은 줄어든다. 하지만 두 사람이 같은 메모를 수정했다면 여전히 나중 요청이 앞선 변경을 덮어쓸 수 있다.

이번에는 실행 DB, 업체, 품명에 **조회 당시의 버전과 현재 버전이 일치할 때만 저장하는 낙관적 락**을 적용했다. NestJS, Prisma 7, PostgreSQL을 사용하는 프로젝트이며, 아래 코드는 핵심 흐름만 남긴 예시다.

## 트랜잭션이 있어도 부족했던 이유

기존 업체 수정은 이미 `Serializable` 트랜잭션 안에서 처리하고 있었다. 실행 DB에도 계약 기간과 추가 데이터의 관계를 검증하기 위한 행 잠금이 있었다.

이 장치들은 서버에서 실행되는 작업의 일관성을 지키는 데 필요하다. 그러나 사용자가 화면에서 데이터를 읽고 생각하고 입력하는 시간 전체가 하나의 DB 트랜잭션인 것은 아니다.

```text
B가 수정 화면 조회 ─── 입력 중 ───────────────── 저장 요청
                       A의 저장 트랜잭션 완료     B의 저장 트랜잭션 시작
```

A의 저장이 끝난 다음 B의 저장 트랜잭션이 시작됐다면, DB 입장에서는 순서대로 처리한 정상적인 작업이다. B가 보낸 연락처가 오래된 화면에서 온 값이라는 사실은 DB가 알 수 없다.

PostgreSQL의 `Serializable`은 동시 트랜잭션의 결과가 직렬 실행과 일치하도록 보장하는 격리 수준이다. 여기서 화면을 열었던 시점의 상태까지 검증하려면 애플리케이션이 그 기준을 함께 전달해야 한다. [PostgreSQL 트랜잭션 격리 문서](https://www.postgresql.org/docs/18/transaction-iso.html)

따라서 기존 트랜잭션과 계약 기간 검증은 유지하고, 사용자 편집의 기준을 확인하는 버전 검사를 추가했다.

## `updatedAt` 대신 `version`을 선택했다

낙관적 락을 구현하는 방법이 정수 버전 하나뿐인 것은 아니다.

| 방식 | 저장 시 확인하는 값 | 이번 적용에서 고려한 점 |
| --- | --- | --- |
| 정수 버전 | 조회 당시 `version` | 변경 여부가 명확하고 시간 변환이 필요 없다 |
| 수정 시각 | 조회 당시 `updatedAt` | 기존 컬럼을 재사용할 수 있지만 정밀도와 갱신 규칙을 확인해야 한다 |
| 기존 필드 값 | 조회 당시 메모·연락처 등 | 필드별 충돌 판단이 가능하지만 함께 검증할 필드가 많아진다 |

`updatedAt`을 쓰면 컬럼 추가를 피할 수 있다. 다만 수정 시각이 안전한 변경 토큰이 되려면 몇 가지 조건을 확인해야 한다.

- DB의 시간 정밀도가 API와 JavaScript를 거쳐도 보존되는가?
- 짧은 간격의 서로 다른 수정이 같은 시각 값으로 기록될 수 있는가?
- 직접 SQL이나 다른 저장 경로에서도 시각이 반드시 갱신되는가?

정밀도 문제가 모든 시스템에서 발생하는 것은 아니다. 하지만 시각 값이 다르다는 조건을 쓰려면, 직렬화 과정과 실제 갱신 방식까지 확인해야 한다.

이번에는 `updatedAt`을 마지막 수정 시각을 보여 주는 용도로 유지하고, 변경 판단에는 `version`을 따로 사용했다. `7 → 8`처럼 증가한 값이 편집의 기준이 된다.

물론 버전도 저절로 관리되지는 않는다. 데이터를 변경하는 모든 경로에서 증가시켜야 한다. Prisma 문서에서도 버전 필드를 사용하는 낙관적 동시성 제어를 설명한다. [Prisma Client의 낙관적 동시성 제어](https://www.prisma.io/docs/orm/v7/reference/prisma-client-reference#optimistic-concurrency-control-on-updates)

## 비교와 저장을 하나의 작업으로 묶기

세 모델에 다음 필드를 추가했다.

```prisma
version Int @default(1)
```

마이그레이션으로 기존 데이터에도 버전 1을 부여한다. 조회 응답에는 버전을 포함하고, 수정 요청은 사용자가 조회했던 버전을 함께 보낸다.

```json
{
  "memo": "다음 주에 다시 연락",
  "version": 7
}
```

서버에서 다음처럼 먼저 조회하고 비교하는 것만으로는 충분하지 않다.

```ts
const current = await prisma.company.findUniqueOrThrow({
  where: { id },
});

if (current.version !== input.version) {
  throw new ConflictException('다른 사용자가 수정했습니다.');
}

// 이 사이에 다른 요청이 저장될 수 있다.
await prisma.company.update({
  where: { id },
  data: { memo: input.memo },
});
```

조건 비교를 통과한 두 요청이 모두 ID만으로 저장하면, 다시 덮어쓰기가 발생할 수 있다. 그래서 **실제 UPDATE의 조건에 버전을 넣고, 같은 작업에서 버전을 증가**시켰다.

```ts
await prisma.company.update({
  where: {
    id,
    workspaceId,
    deletedAt: null,
    version: input.version,
  },
  data: {
    memo: input.memo,
    version: { increment: 1 },
  },
});
```

이 예시는 권한 검증과 입력 검증을 생략한 저장 부분이다. 실제 구현에서는 기존 워크스페이스·담당자·공개 범위 검증을 유지했다. 버전은 접근 권한을 대신하지 않는다.

두 사용자가 모두 버전 7로 저장하면 먼저 성공한 요청이 버전을 8로 바꾼다. 나머지 요청은 더 이상 버전 7인 행을 수정할 수 없다. 정수 버전은 DB가 쓰기 과정에서 사용하는 잠금 자체를 없애는 기능도 아니다. 사용자가 폼을 작성하는 동안 잠금을 점유하지 않고, 저장할 때 변경 여부를 검사하는 방식이다.

## 충돌은 일반 저장 실패와 구분한다

이번 구현에서는 오래된 버전으로 저장하려는 요청에 `409 Conflict`를 반환했다. 버전이 누락됐거나 양의 정수가 아니면 요청 DTO 검증 단계에서 거절한다.

저장 시에는 두 종류의 DB 오류도 함께 처리했다.

| 오류 | 이 저장 경로에서의 처리 |
| --- | --- |
| `P2025` | 조건에 맞는 수정 대상이 없어졌으므로 충돌로 안내 |
| `P2034` | 쓰기 충돌 또는 데드락으로 트랜잭션이 실패했으므로 충돌로 안내 |

`P2025`가 언제나 버전 충돌을 뜻하는 것은 아니다. 삭제되었거나 다른 조건이 맞지 않아도 발생할 수 있으므로, 모든 API의 오류를 무조건 409로 바꾸지 않고 이번 조건부 쓰기 경로에 한정했다. 오류 의미는 [Prisma 오류 코드 문서](https://www.prisma.io/docs/orm/v7/reference/error-reference#prisma-client-query-engine)를 참고했다.

Prisma 문서는 `P2034` 발생 시 트랜잭션 재시도 패턴도 설명한다. 재시도하더라도 사용자가 처음 보낸 버전 조건은 유지해야 한다. 서버가 최신 버전을 가져와 이전 입력에 붙여 다시 저장하면 충돌 검사를 우회하게 된다. 이번 사용자 편집 흐름에서는 충돌을 알려 주고 내용을 다시 확인하도록 처리했다. [Prisma 트랜잭션 문서](https://docs.prisma.io/docs/orm/v7/prisma-client/queries/transactions)

## 수정 API 하나만 바꾸면 끝나지 않는다

코드를 확인하면서 가장 많이 살펴본 부분은 같은 레코드를 변경하는 다른 경로였다.

| 대상 | 연결한 변경 경로 |
| --- | --- |
| 업체 | 일반 수정, 담당자 변경, 계약 해지, 삭제, MCP |
| 품명 | 일반 수정, 가격 변경 이력, 삭제 |
| 실행 DB | 상세 수정, 추가·환불 데이터 수정, 목록의 업체·품명·결제 상태·견적 발송 변경, 삭제, MCP |
| 실행 DB를 참조하는 미수금 | 미수금 정보 수정, 수금 처리에 따른 결제 상태 갱신 |

예를 들어 미수금 화면에서 결제 상태를 바꿨는데 실행 DB 버전이 그대로라면, 이전에 열어 둔 실행 수정 화면이 그 변경을 덮어쓸 수 있다. 따라서 직접 편집하는 미수금 요청에도 기준 버전을 받고, 수금 처리로 결제 상태를 갱신할 때도 실행 버전을 증가시켰다.

품명은 가격과 가격 변경 로그를 같은 조건부 쓰기에 포함했다. 버전 충돌로 거절된 가격 수정의 로그가 남거나, 성공한 다른 수정의 로그가 덮어써지면 안 되기 때문이다. 등록 시에도 품명과 최초 가격 로그를 단일 DB 작업으로 저장하도록 정리했다.

삭제 역시 사용자가 확인한 상태를 기준으로 처리했다. 단건 삭제는 조회 당시 버전을 받고, 실행 DB 일괄 삭제는 ID별 버전을 함께 받는다.

```json
{
  "ids": ["execution-a", "execution-b"],
  "versions": [3, 5]
}
```

ID와 버전의 개수·중복을 검증하고, 트랜잭션 안에서 조건부 삭제 결과를 확인한다. 하나라도 충돌하면 전체를 취소한다. SQL이 일부 행을 변경했더라도 결과 건수가 기대와 다르면 예외를 발생시켜 트랜잭션을 롤백한다.

## 화면도 편집을 시작한 버전을 기억해야 한다

서버에서 버전을 검사하더라도 화면이 최신 버전을 잘못 붙이면 보호가 무너질 수 있다.

```text
1. 버전 7을 조회하고 메모를 작성한다.
2. 다른 사용자가 저장해서 버전이 8이 된다.
3. 백그라운드 재조회가 버전 8을 가져온다.
4. 작성 중인 예전 폼 값에 버전 8을 붙여 저장한다.
```

4번 요청은 서버의 버전 검사를 통과할 수 있다. 하지만 입력 내용은 여전히 버전 7을 보고 작성한 것이다.

따라서 **폼의 입력값과 기준 버전은 함께 관리**해야 한다. 실행 수정 폼은 편집을 시작할 때 버전을 보관하고, 제출 시 그 값을 전달하도록 했다.

```tsx
const [version] = useState(row.version);

const form = useForm({
  defaultValues: initialValues,
  onSubmit: async ({ value }) => {
    await onSubmit(value, version);
  },
});
```

이 예시는 폼의 생명주기가 하나의 편집 세션과 일치한다는 전제가 있다. 다른 레코드를 편집하거나 저장이 성공해 새 기준으로 편집할 때는 폼도 새로 초기화해야 한다. 실제 화면에서는 레코드 ID와 저장 성공 후 갱신하는 키를 사용했다.

또한 `updatedAt`이 바뀔 때마다 폼을 새로 마운트하던 부분을 수정했다. 백그라운드 재조회만으로 컴포넌트가 다시 마운트되면 작성 중인 입력이 사라질 수 있기 때문이다.

업체·품명 모달도 열릴 때의 기준 버전을 유지하고, 숫자·날짜 셀은 편집 시작 시점의 버전을 보관했다. 업체·품명 선택 창은 열었을 때의 저장 콜백을 유지해, 선택하는 동안 원래 행의 기준이 바뀌지 않도록 했다.

충돌 시에는 다음 원칙을 적용했다.

- 모달을 닫거나 입력값을 초기화하지 않는다.
- 다른 사용자가 수정했다는 메시지를 표시한다.
- 버전만 최신으로 교체해서 자동 재저장하지 않는다.
- 사용자가 입력 내용을 보관하고 최신 내용을 다시 확인하도록 안내한다.

최신 값과 내 입력을 나란히 비교하고 병합하는 화면까지 구현한 것은 아니다. 이번 범위는 조용한 덮어쓰기를 차단하고 입력을 유지하는 데 두었다.

## 실제 DB에서 확인한 결과

운영 DB와 분리한 PostgreSQL 17 컨테이너에서 마이그레이션을 적용하고 실제 서비스와 DB를 연결해 확인했다.

| 확인한 상황 | 결과 |
| --- | --- |
| 업체에 같은 버전으로 두 요청 동시 저장 | 하나 성공, 하나 409 |
| 품명에 같은 버전으로 두 요청 동시 저장 | 하나 성공, 하나 409 |
| 실행 DB에 같은 버전으로 두 요청 동시 저장 | 하나 성공, 하나 409 |
| 이전 버전으로 삭제·업체 해지 | 충돌로 거절 |
| 실행 일괄 삭제 대상 중 오래된 버전 포함 | 모든 대상 보존 |
| 미수금 변경 후 이전 실행 버전으로 수정 | 충돌로 거절 |
| 품명 가격 수정 충돌 | 최초 이력과 성공한 수정 이력만 보존 |
| 기존 데이터에 버전 컬럼 추가 | 기존 값 보존, 버전 1 부여 |

전체 마이그레이션 적용 후 Prisma 스키마와의 차이가 없는 것도 확인했다. 기존 서버 테스트 180개, 클라이언트·서버 타입 검사, 서버 빌드, 변경 파일의 lint도 통과했다. 새 테스트 파일이나 케이스를 추가한 작업은 아니며, 위 동시 요청 결과는 격리 DB에서 별도로 실행해 확인한 내용이다.

전체 저장소 검사는 다른 한계가 있었다. 수정하지 않은 UI 패키지의 테스트 의존성과 타입 누락, 클라이언트의 기존 lint 경고 때문에 전체 검사가 통과한 상태는 아니다. 실제 브라우저에서의 폼 조작은 아직 검증하지 않았고, 운영 DB 마이그레이션과 배포도 수행하지 않았다.

배포 시에는 버전 컬럼을 먼저 추가하고, 필수 버전을 보내는 클라이언트와 이를 검증하는 서버를 함께 반영해야 한다. 이미 열려 있는 이전 클라이언트는 버전 없는 요청이 거절될 수 있으므로 새로고침 안내도 고려해야 한다.

## 이번에 선택한 충돌 단위

처음에는 레코드 전체를 하나의 버전으로 관리했다. 따라서 A가 연락처를 수정하고 B가 메모를 수정한 경우처럼 서로 다른 필드를 바꿔도 충돌할 수 있다.

이 제한은 의도적이다. 업체에는 담당자·계약 시작일·해지일처럼 함께 검증해야 하는 정보가 있고, 실행 DB에도 기간·수량·금액 사이의 관계가 있다. 필드별 자동 병합을 먼저 도입하면 어떤 조합을 안전하게 합칠 수 있는지부터 정해야 한다.

실제 사용에서 충돌 빈도와 수정 패턴을 확인한 뒤, 서로 독립적인 필드만 병합하거나 최신 값과 작성한 값을 비교하는 화면을 추가할 수 있다. 현재는 한 사람이 저장한 내용이 다른 사람의 오래된 화면 때문에 조용히 사라지지 않도록 하는 것이 우선이다.
